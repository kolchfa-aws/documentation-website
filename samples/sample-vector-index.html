Creating and searching vector indexes

Applies to

OpenSearch Service domains · OpenSearch Serverless NextGen vector search collections · OpenSearch Serverless Classic vector search collections
For availability of each option on this page, see Feature availability.

A vector index stores numeric vectors, such as embeddings generated by a machine learning model, alongside regular fields. You can search it for the documents whose vectors are closest to a query vector. Use vector search for product recommendations, image and document similarity, and semantic search.

For background on how approximate nearest neighbor search works, see Vector search concepts on the OpenSearch documentation website.

To generate embeddings from text automatically at ingest and search time, see AI search. This page covers indexes into which you load vectors yourself.

Prerequisites

  • An OpenSearch Service domain. For instructions, see Creating and modifying domains.
  • Permission to send requests to the domain:
    • The domain access policy or an IAM policy must allow the es:ESHttpPut, es:ESHttpPost, and es:ESHttpGet actions on the domain.
    • If the domain uses fine-grained access control, your user or role must also be mapped to a role that has index permissions on the vector index. For more information, see Fine-grained access control.
  • A vector search collection. For new collections, use NextGen. For instructions, see Creating and managing collections.
  • An IAM policy that allows aoss:APIAccessAll on the collection.
  • A data access policy that grants you the following permissions on the index:
JSON
[
  {
    "Rules": [
      {
        "ResourceType": "index",
        "Resource": ["index/<collection-name>/*"],
        "Permission": [
          "aoss:CreateIndex",
          "aoss:DescribeIndex",
          "aoss:ReadDocument",
          "aoss:WriteDocument"
        ]
      }
    ],
    "Principal": ["arn:aws:iam::<account-id>:role/<role-name>"]
  }
]

For more information, see Data access policies.

Sending requests

You can send the requests on this page from Dev Tools in OpenSearch Dashboards or OpenSearch UI, or from any HTTP client that signs requests using AWS Signature Version 4. When you sign requests, use the service name es for a domain and aoss for a collection. For more information, see IAM and request signing.

Step 1: Create a vector index

The following request creates an index named products with a 3-dimensional vector field and two metadata fields. The same request works on domains and on both Serverless generations:

JSON
PUT /products
{
  "settings": {
    "index.knn": true
  },
  "mappings": {
    "properties": {
      "product_vector": {
        "type": "knn_vector",
        "dimension": 3,
        "space_type": "l2"
      },
      "name": {
        "type": "text"
      },
      "price": {
        "type": "float"
      }
    }
  }
}

The dimension must match the number of values in the vectors that you index. For the maximum number of dimensions on each deployment, see Quotas and Regions. The space_type is the distance function: l2 (Euclidean distance), cosinesimil (cosine similarity), or innerproduct (dot product).

Choosing the engine, algorithm, and compression

How much of the index configuration you can choose depends on the deployment:

SettingDomainsServerless NextGenServerless Classic
method.engine and method.name You can set them. Which engines are supported depends on the engine version. See OpenSearch compatibility. Not supported. OpenSearch Serverless chooses the configuration. You can set them. The default engine is nmslib.
compression_level Confirm 32x by default. You can set 1x, 2x, 8x, 16x, or 32x. Confirm
GPU acceleration for index builds Off by default. See GPU acceleration. On by default. Use index.knn.remote_index_build.enabled to turn it off for an index. Confirm

The following request creates an index that uses 1x compression (no compression):

JSON
PUT /products-uncompressed
{
  "settings": {
    "index.knn": true
  },
  "mappings": {
    "properties": {
      "product_vector": {
        "type": "knn_vector",
        "dimension": 3,
        "space_type": "l2",
        "compression_level": "1x"
      }
    }
  }
}

Step 2: Index documents

The following request indexes three products:

JSON
POST /_bulk
{ "index": { "_index": "products" } }
{ "product_vector": [0.12, 0.85, 0.33], "name": "Trail running shoes", "price": 129.99 }
{ "index": { "_index": "products" } }
{ "product_vector": [0.10, 0.80, 0.40], "name": "Lightweight hiking boots", "price": 159.00 }
{ "index": { "_index": "products" } }
{ "product_vector": [0.90, 0.15, 0.05], "name": "Insulated water bottle", "price": 24.50 }

The following options depend on the deployment:

DomainsServerless NextGenServerless Classic
Custom document IDs (PUT /products/_doc/<id>) Supported Supported Not supported. Omit the document ID, and OpenSearch Serverless generates one.
Time until new documents are searchable Controlled by the index's refresh_interval setting About 5 seconds About 60 seconds

Step 3: Search the index

The following request returns the two products whose vectors are closest to the query vector:

JSON
GET /products/_search
{
  "size": 2,
  "query": {
    "knn": {
      "product_vector": {
        "vector": [0.11, 0.82, 0.36],
        "k": 2
      }
    }
  }
}

Set size as well as k. Without size, a domain can return k results for each shard instead of k results in total.

Vectors in the response: On domains and Classic collections, each hit's _source includes the vector field. On NextGen collections, _source excludes vectors by default, which reduces response size and latency. To include the vector field on NextGen, add "_source": true to the request, or list the field in _source.includes.

JSON
{
  "took": 8,
  "timed_out": false,
  "hits": {
    "total": { "value": 2, "relation": "eq" },
    "max_score": 0.99,
    "hits": [
      {
        "_index": "products",
        "_id": "1",
        "_score": 0.99,
        "_source": {
          "name": "Trail running shoes",
          "price": 129.99
        }
      },
      {
        "_index": "products",
        "_id": "2",
        "_score": 0.98,
        "_source": {
          "name": "Lightweight hiking boots",
          "price": 159.00
        }
      }
    ]
  }
}

Filtering results

To return only documents that match a condition, add a filter inside the knn query. The following request returns the closest products that cost less than 150:

JSON
GET /products/_search
{
  "size": 2,
  "query": {
    "knn": {
      "product_vector": {
        "vector": [0.11, 0.82, 0.36],
        "k": 2,
        "filter": {
          "range": {
            "price": { "lt": 150 }
          }
        }
      }
    }
  }
}

Filtering inside the knn query requires an engine that supports it. See OpenSearch compatibility.

Limitations

LimitationDomainsServerless NextGenServerless Classic
k-NN cluster settings You can change all of them except knn.memory.circuit_breaker.enabled and knn.circuit_breaker.triggered Not applicable Not applicable
Warmup, stats, and model training APIs Confirm Confirm Not supported
Inline and stored scripts Supported Confirm Not supported
Radial search Confirm Not supported on indexes that use 32x compression Confirm
UltraWarm and cold storage Supported for k-NN indexes created on 2.x or later, on domains running 2.17 or later Not applicable Not applicable

On domains, vector graphs use memory outside the Java heap. By default, k-NN uses up to half of the memory that isn't allocated to the heap, which is a quarter of the instance's RAM. Monitor the KNNGraphMemoryUsage CloudWatch metric to watch graph memory. For more information, see CloudWatch metrics.
